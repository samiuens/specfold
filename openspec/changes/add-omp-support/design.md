# Design

## Context

See proposal.md (Why). Facts about omp, taken from its bundled docs (`omp://skills.md`, `context-files.md`, `task-agent-discovery.md`, `hooks.md`, `settings.md`, `approval-mode.md`, `environment-variables.md`) on 2026-11-15 and from this session's environment:

- **Instructions and skills.** omp loads `AGENTS.md`. It reads skills from `.agents/skills/` and `.claude/skills/` and drops a symlinked copy by realpath, so the sf skills appear once.
- **Roles.** Task agents come only from `.omp/agents/*.md`; `.claude/agents/` is skipped on purpose. The frontmatter fields are `name`, `description`, `tools`, `spawns`, `model` (a selector or a role alias such as `@smol`), `thinking-level` and `autoload-skills`. A project agent named `scout` overrides omp's bundled `scout`.
- **Subagents.** They run headless. Any call that resolves to a prompt is rejected there, and `task.maxRecursionDepth` caps nesting. Isolation is per task (`isolated: true`) and needs `task.isolation.enabled`; `task.isolation.merge: branch` commits a task's work to a branch, and `task.isolation.apply: false` keeps it from being applied to the parent.
- **Hooks.** Hooks are TS factories in `.omp/hooks/pre|post/*.ts` that call `pi.on(event, handler)`. Useful events: `before_agent_start` (inject a message), `tool_call` (block), `tool_result` (`additionalContext`) and `agent_end`, which cannot block.
- **Bash rules.** `bash.patterns` in `.omp/config.yml` is an ordered list of `{match, approval}` with `allow | prompt | deny`. The first match wins, and `*` is the only wildcard. Project rules are prepended to global ones and can tighten but never loosen the operator's rules.
- **Environment.** omp's bash tool sets `PI_SESSION_ID` on every agent command (documented) and `OMPCODE=1` (observed). It also sets `CLAUDECODE=1`, so `CLAUDECODE` alone does not mean Claude Code. User `!` commands get neither.

In the CLI, `parseTools` and `TOOLS` live in `src/migrate/install.ts` (`agents`, `claude`). The upgrader derives tools from the manifest (`toolsOf`). `agents sync` lives in `src/agents/`, the permission rendering in `src/permissions/`, and the Claude hook subcommands in `src/hooks/claude.ts`.

## Goals / Non-Goals

**Goals:**
- One source per role and per check: omp files are generated from, or forward to, what Claude Code already uses.
- Nothing changes for a repository that does not list `omp`.

**Non-Goals:**
- A planner for omp, read barriers for omp, and the duplicate `openspec-*` skills (brief, out of scope).
- Making `bash.patterns` a sandbox. Like the Claude rules, they are best effort, and `AGENTS.md` stays the contract ([agent permissions](/decisions/agent-permissions.md)).
- An `omp` doctor check. `agents sync --check` and `permissions sync --check` cover drift.

## Decisions

1. **`tools` lives in `src/repo.ts`.** `Config.tools` is parsed and validated there. The default is derived from `agents.targets`, so repositories from earlier releases read exactly as they behave today.
   - `TOOLS` gains `omp`, and `parseTools` accepts any list that holds `agents`. The usage error lists the allowed ids.
   - `openspecInit` filters out `omp`.
   - `toolsOf` in the upgrader reads `config.tools` when the key exists and falls back to its manifest rule otherwise.
   - Alternative rejected: deriving omp from the manifest (presence of `.omp/` files), as `toolsOf` does for Claude. The brief chose an explicit setting (Q3), and a setting is what init and migrate write.

2. **Signing agent writes.** One helper, `agentBy(config, model, env)`, replaces the three copies of `` `${config.agentPrefix}${model}` `` in `new`, `backlog` and `sync`.
   - It returns `omp/<model>` when `OMPCODE` or `PI_SESSION_ID` is non-empty, and `agent_prefix + model` otherwise.
   - `PI_SESSION_ID` is the documented marker; `OMPCODE` is checked too because it is cheaper to read and was observed.
   - `verify`'s `AGENT_VARIABLES` gains both.

3. **Role generation** lives in a new `src/agents/omp.ts` with pure planning (source text in, file text out) and I/O in `sync.ts`/`command.ts`, the same split as permissions. Mapping:

   | Claude key | omp key |
   | --- | --- |
   | `name`, `description` | same |
   | `model: haiku / sonnet / opus` | `model: "@smol" / "@default" / "@slow"`; another value is dropped, so the role inherits the session model |
   | `effort` | `thinking-level` |
   | `skills` | `autoload-skills` |
   | `tools` (CSV) | list, mapped `Read→read`, `Grep→grep`, `Glob→glob`, `Bash→bash`, `Write→write`, `Edit→edit`, `WebSearch→web_search`, `AskUserQuestion→ask`, `Agent→task`; unmapped names dropped |
   | `disallowedTools` containing `Agent` | `spawns: ""` |
   | `maxTurns`, `isolation`, `hooks`, `permissionMode`, `ExitPlanMode` | dropped |

   - **Marker.** The body's first line is `<!-- generated by specfold agents sync from .claude/agents/<name>.md; edit that file -->`. omp passes the body as the system prompt, and the comment costs a few tokens. An unknown frontmatter key was rejected as the marker, because omp's parser behavior for it is not documented.
   - **The dropped keys' jobs move elsewhere.** `isolation: worktree` becomes `isolated: true` on the sf-apply dispatch (decision 7), and the implementer's no-push hook becomes the adapter's subagent guard (decision 6).
   - **`planner` is skipped by name.** omp subagents can't ask the user (brief Q6).
   - **Ownership.** A file is the sync's own when it starts with the marker; otherwise it is reported as `kept`. The JSON `actions` entry keeps `{path, action, target}`, where `target` is the source path for `write` and `rewrite`.
   - **An `.agents/skills/` folder is not required.** Generation runs whenever `omp` is listed.

4. **omp task settings** are edited with the `yaml` Document API, as `parallel/limit.ts` does, so comments and long lines survive. The sync owns four keys: `task.maxRecursionDepth: 1`, `task.isolation.enabled: true`, `task.isolation.merge: branch` and `task.isolation.apply: false`.
   - `apply: false` keeps sf-apply's own merge step: the orchestrator merges each implementer's branch, as it does for Claude Code worktrees.
   - The personal subagent limit is not written here (brief Q9, revised): `.omp/config.yml` is committed.

5. **omp permission rules.** The patterns come from `ACTION_TABLE` by stripping `Bash(` and `)`. For each pattern ending in ` *`, the bare command (`git push`, `gh pr create`) is owned as well, because omp's `*` is not documented to match nothing after a space. `ask` is rendered as `prompt`.
   - **Ownership** is the set of `match` strings, current and `RETIRED` alike. On each run, owned entries are taken out and re-emitted as one block at the start: deny, then prompt, then allow. First-match order makes the strictest sub-action win, which is the same invariant Claude Code gets from its deny-ask-allow precedence ([agent permissions](/decisions/agent-permissions.md)).
   - **Reporting.** `planPermissions` returns a second plan for `.omp/config.yml`. `Change` gains a `target` field, and the omp levels are reported as `prompt`, not `ask`.
   - Alternative rejected: appending the block, as for Claude Code. A team `allow` rule placed earlier would then shadow the Specfold rules.

6. **Hook adapter.** It ships as `template/.specfold/tools/omp/hooks/pre/specfold.ts`, an inactive copy installed only with `omp`. This is the same shipped/active pattern as `UPGRADE_WORKFLOW` (`.specfold/workflows` → `.github/workflows`).
   - It imports only types from omp, so it loads in omp and in vitest alike.
   - It runs the CLI with `spawnSync(process.execPath, ["scripts/specfold.mjs", "hook", name], {cwd: repo root, input, timeout: 60s})` and swallows every failure.

   | omp event | Condition | Subcommand | Effect |
   | --- | --- | --- | --- |
   | `before_agent_start` | main session, first run | `claude-session-start` | stdout as injected message |
   | `tool_result` | `edit`/`write`, not `isError`, per path in `input.path`/`input.paths` | `claude-post-tool-use` with a Claude-shaped event | exit 2 → stderr as `additionalContext` |
   | `agent_end` | main session | `claude-stop` | exit 2 → `pi.sendMessage` follow-up with stderr |
   | `tool_call` | subagent session, `bash` | `claude-no-push` with `{tool_input:{command}}` | exit 2 → `{block: true, reason: stderr}` |

   - **Subagent detection** is the adapter's one omp-specific judgment. Task 1.1 settles it against the installed omp: candidates are a task-depth or parent-session field in the hook context or session manager. `ctx.hasUI` is a fallback only, because print-mode main sessions lack a UI too. The spec states only "task subagent session", so the choice doesn't change it.
   - **Pushes in subagents.** With `push: ask`, a subagent's push already resolves to `prompt` and is rejected headless. The guard covers `push: allow` and the forms the patterns miss (brief open question 2).
   - **Stop loop.** Claude Code's Stop hook also reruns until the gate is clean, so the follow-up loop is the intended behavior. The adapter sends at most one follow-up per `agent_end`.

7. **sf-apply on omp.** A new section in `template/.agents/skills/sf-apply/SKILL.md` covers dispatch in omp:
   - implementers through the `task` tool with `agent: implementer` and `isolated: true`;
   - at most `specfold parallel show` tasks per batch;
   - merging the branch omp reports for each task;
   - `verifier` and `knowledge-curator` without isolation.

   Task 1.1 records the actual branch name omp reports, and the section names it. `sf-plan` needs no change.

8. **Template and kit.**
   - **Settings.** `template/specfold.yaml` gets `tools: [agents, claude]` with a comment naming `omp`.
   - **Kit-owned files.** `kitOwned` adds `.claude/agents` when `claude` or `omp` is listed, plus `.specfold/tools`. The active adapter copy is handled like the active upgrade workflow in init, migrate and upgrade.
   - **AGENTS.md.** `template/AGENTS.md` says that omp reads `.agents/skills/` directly and plans with `sf-plan`. The kit's `AGENTS.md` changes `claude-code/<model>` to `<tool>/<model>` (`claude-code/` or `omp/`) and stays under its G11 budget.
   - **Delegated:** the kit repo itself lists `omp` in `tools`, so the kit dogfoods the omp files ([self-hosting](/decisions/self-hosting.md)).

## Risks / Trade-offs

- **[Risk] omp's hook and settings APIs are internal to omp and can change.** → The adapter swallows failures, and a new Reference concept records the facts with a short `stale_after`. Task 1.1 checks every fact this design relies on against the installed omp.
- **[Risk] `OMPCODE` is undocumented.** → `PI_SESSION_ID` is documented and checked too.
- **[Risk] omp's `*` matching may differ from Claude Code's for some forms.** → Owning the bare forms covers the known gap. Tests check one matching and one non-matching command per action, using a matcher that follows omp's documented semantics, as add-agent-permissions did for Claude Code.
- **[Risk] Shells started through omp's `eval` tool bypass `bash.patterns`.** → This is documented in the Reference concept and the capability card. The rules stay best effort, and `AGENTS.md` is the contract.
- **[Trade-off] Project `allow` rules can't loosen an operator's global `prompt` or `deny`.** → An `allow` level in `specfold.yaml` is a ceiling under omp, which matches the intent of a setting written into a repository the agent can edit.
- **[Trade-off] An omp-only repository carries `.claude/agents/` as the role source.** → The files are small, and one source beats a second template copy.
- **[Risk] Generated roles drift when someone edits `.claude/agents/` and forgets the sync.** → `agents sync --check` reports it. Upgrade already runs `agents sync` as a follow-up, and the pre-commit hook can run the check through `hooks.extra`.

## Migration Plan

Nothing changes until a repository adds `omp` to `tools` (or runs `init`/`migrate install` with it). After that, `specfold upgrade --yes` (also at the installed version) or `agents sync` plus `permissions sync` plus a copy of the adapter sets it up. To roll back, remove `omp` from `tools` and run `agents sync`, which removes the generated roles. Then delete `.omp/hooks/pre/specfold.ts` and the owned `.omp/config.yml` keys by hand.

## Open Questions
